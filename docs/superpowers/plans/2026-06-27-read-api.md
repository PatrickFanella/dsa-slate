# Read API Implementation Plan

> **For agentic workers:** Execute this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a minimal read-only Go API for the source-linked directory so the frontend can later move from static TypeScript seed data to backend-provided records.

**Architecture:** Build a small standard-library HTTP server first, with explicit JSON contracts and health endpoints. Use PostgreSQL for the API source of truth in this slice, seeded from SQL fixtures that mirror the current California static data. Keep the frontend on static data until the API is verified, then switch it in a later slice.

**Tech Stack:** Go standard library HTTP server, PostgreSQL, Docker Compose, SQL migrations/seed fixture, Go tests, existing Makefile verification.

---

## Prerequisite

Start this API slice only after the methodology/disclaimer slice is implemented and verified. The API should not change public trust/disclaimer copy, and the frontend should remain on static seed data until this backend contract is independently verified.

## Scope

- Add a running Go HTTP API instead of the current service-name placeholder.
- Add `GET /healthz`.
- Add `GET /api/directory` returning chapters, elections, races, candidates, voter guides, endorsements, ballot measures, and measure positions.
- Add explicit dev seed fixture for the current California cluster.
- Add Makefile command to apply seed data separately from schema migrations.
- Keep the API read-only.
- Keep frontend on static data in this slice; frontend API integration is next.

Out of scope:

- auth/admin writes
- public submission flow
- address/ZIP lookup
- pagination
- complex filtering/search in SQL
- replacing frontend static data immediately

## Open decision before implementation

Recommended: DB-backed API with a separate `seeds/california.sql` fixture and `make seed` command. Keep seed data outside numbered schema migrations so future `make migrate` behavior does not accidentally seed non-dev environments.

Alternative: static in-memory API that embeds a JSON fixture. Faster, but creates another source of truth and delays database proof.

## API contract

`GET /healthz`

```json
{"ok":true,"service":"dsa-slate"}
```

`GET /api/directory`

```json
{
  "chapters": [],
  "elections": [],
  "races": [],
  "candidates": [],
  "voterGuides": [],
  "endorsements": [],
  "ballotMeasures": [],
  "measurePositions": []
}
```

JSON field names should match frontend TypeScript casing (`sourceUrl`, `chapterId`, `electionId`, `endorsementType`, `sourceDate`, `publishedAt`, etc.) so frontend integration stays simple.
